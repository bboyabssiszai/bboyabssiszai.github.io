# Agentic RSI：问题与思考

赵子博 · CumberBear / 发布于 2026 年 11 月 1 日

从上下文、策略、编排与状态更新出发，讨论 Multi-Agent、Workflow、Skill，以及系统如何从运行轨迹中改进自身。

这组问答记录了我对 Agent 系统设计的一些理解。贯穿其中的视角是：先明确系统的哪些模块发生了变化，再讨论架构名称与实现形式的差异。

## 01 用四个模块理解 Agent

Prompt engineering、context engineering 和 harness engineering 分别解决什么问题？我倾向于先把 Agent 的一次运行拆成四个模块，再讨论不同系统之间的区别。

系统先从完整状态中构造上下文，由模型提出动作，再经过调度和约束决定实际执行的动作，最后接收环境反馈、更新状态。

$$
\begin{aligned}
c_t &\sim Q_{\phi}(c_t\mid s_t) && \text{构造上下文} \\
u_t &\sim \pi_{\theta}(u_t\mid p,c_t) && \text{模型提出动作} \\
a_t &\sim G_{\eta}(a_t\mid s_t,u_t) && \text{调度、约束与执行决策} \\
s_{t+1} &\sim T_{\eta}(s_{t+1}\mid s_t,a_t) && \text{环境反馈与状态更新}
\end{aligned}
$$

一次循环：Q → π → G → T。

-   **sₜ**：完整系统状态，包括环境状态、历史、记忆和运行状态。
-   **cₜ**：本轮送给模型的上下文。
-   **uₜ**：模型提出的输出或动作；**aₜ**：系统实际执行的动作。
-   **p、φ、η**：分别表示 prompt、context 和 harness 配置。

将这些环节合在一起，就得到系统从一个状态转移到下一个状态的描述：

$$
K_{p,\phi,\eta}(s'\mid s)=\sum_{c,u,a}Q_{\phi}(c\mid s)\,\pi_{\theta}(u\mid p,c)\,G_{\eta}(a\mid s,u)\,T_{\eta}(s'\mid s,a)
$$

| 工程方式 | 主要改变什么 | 直接作用 |
| --- | --- | --- |
| Prompt engineering | 模型策略中的 p | 给定信息后，模型倾向于做什么 |
| Context engineering | 上下文构造 Q | 模型获得哪些信息，以什么形式获得 |
| Harness engineering | G、T 以及整体编排 | 哪些动作实际发生、怎样反馈、何时继续或停止 |

在我看来，上下文操作最终都是为了获得更好的轨迹分布，从而更好地解决问题。以多轮聊天为例：当轮次增加、问题变复杂，已有历史无法完整传递到下一轮时，就需要先构造 cₜ，再注入指令 p，随后通过编排决定如何处理，并更新系统状态。

## 02 为什么使用 Multi-Agent

AgentX 为什么选择 Multi-Agent，而不是“单 Agent＋多工具＋知识库”？首先需要讨论理想情况：如果两种实现中对应的模块完全一样，它们当然可以没有区别。

如果单 Agent 在每一步都能构造相同的上下文 cₜ、使用相同的角色指令 pₖₜ，并拥有相同的工具和执行规则，那么在相同模型和采样设置下，两者可以产生相同的动作分布；逐步执行，也可以得到相同的轨迹分布。

$$
P_{\mathrm{single}}(a_t\mid p_{k_t},c_t)=P_{\mathrm{multi}}(a_t\mid p_{k_t},c_t)
$$

Multi-Agent 的实际价值在于：**在有限上下文预算下，让每个角色只接收与当前决策相关的信息，减少无关历史对判断的干扰。**

如果单 Agent 能够在角色切换时，先从系统状态构造合适的上下文，再注入下一角色的指令，那么它实际上也实现了类似 Multi-Agent 的角色切换与记忆机制。这个机制可以由模型决策，也可以由规则约束；前者会引入一定的随机性，后者则需要明确的系统规则。

因此，我更关注的是：通过一套 System Rule，约定不同模块产出的状态 sₜ，以及下一模块需要的上下文 cₜ。这样的接口约定，是提高协作效率的关键。

## 03 Agent 与 Workflow 的边界

“这个系统看起来更像 Workflow”，是一个经常出现的问题。我的理解是，Workflow 是一套规则，对角色指令、上下文和下一步状态有更明确的约定；Agent 的决策空间则相对更抽象、更开放。

两者可以协同工作：**Workflow 控制宏观规则，Agent 负责规则内的微观决策。**当我们设置角色指令和运行边界时，系统本身就已经具有 Workflow 的一面。快应用中的流程，以及我们构建的 SOP，都可以从这个角度理解。

## 04 AgentX 与 Codex 的区别在哪里

仍然可以用四个模块来比较。如果讨论 Multi-Agent 和 Single-Agent，关键差异在上下文构造 Q；如果都采用 Single-Agent，重点就转向编排 G。

$$
K_X=Q_X\pi_X G_X T_X \qquad \text{vs.} \qquad K_C=Q_C\pi_C G_C T_C
$$

这里用模块乘积简写系统组成，完整状态转移见第一节。

我的理解是，Codex 面向更通用的任务，编排需要兼顾通用规则和具体目标，可以概念性地记为 G\_general＋G\_goal；AgentX 则围绕特定目标组织 G\_goal。这是我用于讨论系统设计的抽象，并非对产品内部实现的断言。

我们当然可以用 Codex 作为基座。需要处理的是：如何通过额外规则，让通用编排服务于特定目标，以及这些规则随时间积累后，如何保持系统可维护。

## 05 RSI 改进的是记忆还是系统

从 Trace 中抽象经验，与从 Trace 中直接重构架构，区别是什么？在这里的划分中，前者主要通过 Q 影响后续运行，更接近记忆的整理与调用；后者则同时改变 Q、π 和 G，需要更系统地调整上下文、策略与编排。

我不认为两者有绝对的好坏。我的一个判断是：**编排 G 本身的迭代正在变快。**经验既可以被保存为下一次运行的输入，也可以进一步转化为系统运行方式的改变。

这也解释了为什么不同问题需要不同的编排。G 可以由 g₁、g₂、g₃ 等子结构组成，每个子结构采取不同形式；面对不同类型的问题，可以把不同的解决思路通过路由组合起来。我认为这与 MoE 的思路有相似之处。

## 06 Personal Agent 需要什么

以 Muse 和 Codex 这类系统的比较为例，我认为关键在于长期用户状态，也就是用户理解。

$$
K_{\text{任务}}(s'\mid s,\text{当前目标}) \qquad \text{vs.} \qquad K_{\text{个人}}(s'\mid s,\text{长期用户状态})
$$

Personal Agent 包含长期状态维护、按需回忆和主动行动控制。如果 Codex 配上同样的 Q、T、G，它也可以承载 Personal Agent；底层模型 π 不一定需要更换。

## 07 Skill 是一种表达方式

为了实现同一个目的，我们可以采用不同的实现方式。Skill 的价值之一，是提供一种表达和组织这些做法的形式。

一个 Skill 可以涉及 Q、π、G、T：如何构造上下文、如何影响模型策略、如何调度动作，以及如何处理环境反馈后的输出。它也因此塑造了人们对 Agent 工作方式的整体印象。

## 08 回到 AgentX 的实践

### 如何增加探索的多样性

多样性问题可以从不同模块入手：

-   从 G 入手：增加多路种子 prompt 的编排。
-   从 T 入手：调整知识检索工具的交互与反馈方式。
-   从 Q 入手：修改上一轮回流到本轮的上下文。

### 如何组织团队知识

团队知识往往是分散的。除了整理过去的知识，还可以约定未来的 LR 文档按 Agent 可使用的格式编写，让新知识从产生时就更容易进入后续流程。

### Agent 搜参与贝叶斯搜参

我认为 Agent 搜参的特点主要在 G 层：它处于更高层的编排位置，而贝叶斯搜参可以成为 Agent 的一种工具。不同公式、不同问题可能需要不同的处理方式，Agent 要决定的是如何组织这些方法。

对于 Agent 的工作风格，我仍然倾向于直接、有效。
